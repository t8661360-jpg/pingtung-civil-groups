## 🔄 工作流

### 1. 反饋收集階段 (11/12-11/15)
- **來源**: 前端漂浮按鈕 + 表單
- **存儲**: localStorage (本地)
- **批次同步**: 每天 03:00 UTC

### 2. 反饋分類階段 (11/16)
- **自動標籤**: type-error, type-missing, type-clarity, type-suggestion
- **優先級判定**: P0-critical, P1-high, P2-medium, P3-low
- **人工審查**: 開發者檢查所有 P0/P1 問題

### 3. 修復階段 (11/17-11/18)
- **高優先修復**: P0/P1 在 24 小時內修正
- **規則補充**: P1-high 漏洞補充新規則
- **表述改進**: P2-medium 可併入下一輪開發

### 4. 驗證階段 (11/19)
- **回歸測試**: 修復後重跑所有測試
- **用戶反饋**: 是否解決原始問題
- **關閉 Issue**: 已驗證解決的 issue 標記 resolved

## 🔗 GitHub Issue 範例

### Issue: 改選完多久要做帳
```
【反饋】誤答 - 改選完多久要做帳

## 反饋詳情

**提問**: 改選完多久要做帳
**系統答案**: 改選後帳務處理：同年度決算於年終前三個月內完成

**反饋內容**:
答案只提到「年終前三個月」，但沒有提到需要在改選後 15 日內完成移交。
用戶實際上問的是改選後立即要做什麼，不是決算期限。

**Session ID**: `session_1699849200_abc123`
```

**標籤**: `feedback`, `type-error`, `priority-P0-critical`

## 🛠️ 自動化流程

### 每日 03:00 UTC 執行
1. 檢查 localStorage 中的待發佈反饋
2. 為每條反饋開立 GitHub Issue
3. 自動標籤分類
4. 發送 Slack/郵件通知

### 每週一 00:00 UTC 執行
1. 統計過去 7 天的反饋
2. 生成週報 Issue
3. 計算關鍵指標
4. 發送管理者報告

### 每月初 00:00 UTC 執行
1. 歸檔上月 Issue
2. 更新統計儀表板
3. 評估系統質量
4. 規劃下月改進

## 📝 反饋分類規則

### 優先級判定矩陣

| 類型 | 單次 | 2-3人 | 4+人 | 判定 |
|------|------|--------|------|------|
| 誤答 | P1 | P1 | P0 | 立即修復 |
| 漏洞 | P2 | P1 | P0 | 補充規則 |
| 表述 | P3 | P2 | P1 | 改進措辭 |
| 建議 | P3 | P3 | P2 | 評估價值 |

### 響應時限

| 優先級 | 響應時限 | 修復時限 |
|--------|---------|---------|
| P0-critical | 1 小時 | 4 小時 |
| P1-high | 4 小時 | 24 小時 |
| P2-medium | 1 天 | 3 天 |
| P3-low | 3 天 | 1 週 |

## 🔐 隱私與安全

### 收集的數據
- 問題文本
- 系統答案
- 反饋內容
- 時間戳記
- 匿名 Session ID

### 不收集的數據
- 用戶身份 (IP、Cookie 等)
- 地理位置
- 個人信息
- Cookie/追踪

### 數據保留期
- 本地 localStorage: 永久 (用戶可清除)
- GitHub Issue: 依照 GitHub 政策
- 備份日誌: 90 天
